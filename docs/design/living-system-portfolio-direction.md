# Living System Portfolio Direction

Status: Frozen direction / pre-development checkpoint

Date: 2026-08-02

This document records the agreed direction for the next portfolio renewal experiment. It freezes the strategic and visual intent before any implementation begins.

## Core Theme

The portfolio should evolve into a mature **Living System**.

The concept may also be described as a **Living World**, but it must remain professional and subtle. The website should not feel like a game, theme park, futuristic control room, or generic developer portfolio.

The experience should feel like one connected professional world in which visitors can understand how Fauzan moves from business problems to systems, analysis, and practical outcomes.

## Professional Identity

Primary identity:

```text
Analytical Systems Builder
```

Core positioning:

```text
From problems and data to system design, insights, and AI-powered workflows.
```

The website should present Fauzan as someone who:

- understands business and operational problems;
- maps processes and relationships;
- structures data and business logic;
- creates reporting, dashboards, automation, and practical workflows;
- uses AI-assisted development as an accelerator;
- applies human business judgment before technology.

The website must not present Fauzan as a pure software developer, generic dashboard builder, or flashy AI engineer.

## Mature Interpretation of the Theme

The agreed combination is:

1. **Editorial Casebook** as the overall foundation
   - calm, professional, readable, and recruiter-friendly;
   - strong typography and clear business storytelling;
   - evidence-led case-study presentation.

2. **Systems Canvas** inside project and reasoning sections
   - process maps;
   - connected stages;
   - business-problem-to-output journeys;
   - restrained interaction that clarifies relationships.

3. **Analytical Workspace / Systems Lab** only for experiments
   - AI-assisted workflows;
   - Personal OS;
   - agent orchestration;
   - Telegram controller;
   - other experimental systems after they are mature enough.

The experimental layer must not dominate the professional identity.

## Possible Website World Structure

The Living System may later use a connected-world structure such as:

- **Home** — entrance and professional overview;
- **Systems District** — ERP, operations, reporting, dashboards, and automation;
- **Market Observatory** — investment analytics and market thinking, only when mature and relevant;
- **Systems Lab / Workshop** — experiments and AI-assisted building;
- **About / Life & Play** — personal dimension, used carefully and without distracting from the professional story.

These names are directional concepts, not approved navigation labels. Exact navigation will be decided during concept review.

## Public Content Maturity Gate

The portfolio is curated evidence, not a complete archive of every project.

Every project must be classified before publication:

### Featured

A project can be featured only when it has:

- a real and understandable problem;
- a coherent business story;
- credible public-safe evidence;
- a stable enough result;
- clear explanation of Fauzan's contribution;
- visuals strong enough to support the story.

### Supporting Evidence

Smaller proven work may appear inside experience or capability sections without receiving a full project page.

### Hold Back

Projects remain private or unlisted while they are:

- incomplete;
- insufficiently validated;
- difficult to explain;
- visually weak;
- confidential;
- not yet mature enough to strengthen the portfolio.

The website should not be filled with immature projects simply to make it appear larger.

## Current Project Positioning

### Strongest current flagship

- Odoo ERP Analytics

This remains the strongest public proof because it connects business problems, ERP process understanding, data logic, review, reporting, and AI-assisted execution.

### Hold back for now

- Telegram Codex Controller;
- Personal OS;
- agent orchestration experiments;
- unfinished prototypes;
- projects without a clear public-safe story.

The Telegram controller may later become a Systems Lab case study after it is working reliably, validated end to end, and safe to present publicly.

## Frontend Skill Experiment

The next frontend renewal should test a mature third-party frontend skill before creating a heavily customised portfolio-specific skill.

The experiment model is:

```text
External mature frontend skill
+ repository guardrails
+ approved visual concept
+ one bounded implementation slice
```

The external skill controls professional design and implementation method. It does not control portfolio identity, project selection, or business claims.

The responsibilities should remain separate:

| Layer | Responsibility |
| --- | --- |
| External frontend skill | Design and implementation workflow |
| Repository rules / AGENTS.md | Permanent identity, boundaries, and safety rules |
| Approved visual concept | Exact visual source of truth |
| Current task prompt | The one small surface being worked on |

## Pre-Development Phases

No development should begin before these phases are completed.

### Phase 1 — Freeze the theme

This document completes the first strategic freeze.

### Phase 2 — Curate public content

Classify candidate projects as Featured, Supporting Evidence, or Hold Back.

### Phase 3 — Inspect the external frontend skill

Review the complete skill before installation or use. Check whether it:

- supports the existing static HTML/CSS architecture;
- forces a framework migration;
- requires visual concepts before coding;
- preserves existing designs;
- verifies browser fidelity;
- risks unnecessary complexity;
- requires unavailable tools.

### Phase 4 — Establish repository guardrails

Create a compact `AGENTS.md` only after its exact rules are reviewed and approved.

Expected rules include:

- preserve Analytical Systems Builder positioning;
- use the mature Living System direction;
- business story before technology;
- no fake metrics, projects, or claims;
- only mature projects appear publicly;
- public site stays unchanged until local approval;
- continue from the existing implementation;
- no framework migration without approval;
- one representative surface at a time.

### Phase 5 — Define one representative experiment

The first experiment should test whether the skill can translate the Living System concept into a mature, credible interface.

Recommended scope:

```text
Homepage first viewport
+ transition into the next section
```

The current live homepage remains untouched during the experiment.

### Phase 6 — Create bounded concept options

Test two interpretations of the same agreed theme, not unrelated visual themes:

- Living System Editorial;
- Living World Interface.

Both must use real content and avoid fake evidence.

### Phase 7 — Approve the visual specification

Lock exact copy, layout, typography, colors, spacing, navigation, system-map treatment, motion, and mobile behaviour before implementation.

## Local Development and Review Phases

### Phase 8 — Isolated local implementation

Use a local branch or worktree. Do not change or deploy the live website.

### Phase 9 — Implement one approved slice

Implement only the approved representative surface and stop.

### Phase 10 — Local visual review

Run the website locally and compare the browser result against the approved concept at desktop and mobile viewports.

### Phase 11 — Evaluate the skill

Review both:

- the visual result;
- the workflow performance of the external skill.

Check for design drift, invented content, architecture changes, verification quality, correction effort, and usage efficiency.

### Phase 12 — Decide the skill strategy

Choose whether to:

- keep the external skill unchanged;
- add a small portfolio-specific wrapper;
- modify selected instructions;
- reject it and test another skill.

### Phase 13 — Expand gradually

Expand only after the representative slice is approved:

```text
Homepage foundation
-> Odoo ERP Analytics case study
-> experience and evidence
-> supporting pages
-> optional Systems Lab later
```

### Phase 14 — Publish after full local approval

Verify content safety, links, responsive behaviour, analytics, and visual consistency before committing the final implementation to the live site.

## Hard Boundaries

Until the pre-development phases are complete:

- do not redesign the whole website;
- do not generate another unrelated full portfolio concept;
- do not modify production HTML or CSS;
- do not publish immature projects;
- do not add the Telegram controller to the public website;
- do not migrate frameworks;
- do not treat visual attractiveness alone as approval;
- do not proceed from concept to implementation without an explicit approval gate.

## Current Frozen Decision

The agreed next direction is:

```text
A mature Living System portfolio
built on an Editorial Casebook foundation,
using Systems Canvas interactions,
with experimental work reserved for a future Systems Lab.
```

The next action is Phase 2: curate the public content before selecting and testing the external frontend skill.
