# Portfolio Development Workflow

Status: Active  
Purpose: Standard workflow for future portfolio updates

---

## Why This Workflow Exists

The portfolio improved most when development stopped starting from implementation.

The strongest updates happened when the process began with visitor psychology, story, content, and visual metaphor before touching HTML or CSS.

This workflow exists to prevent future updates from jumping too quickly into design or code.

---

## Required Workflow

Every major homepage feature, case study section, or design change should follow this order.

```text
1. Observation
2. Visitor Question
3. Desired Emotion
4. Story
5. Content
6. Visual Metaphor
7. Interaction
8. Prototype
9. Implementation
10. QA
11. Reflection
12. Documentation
```

---

## 1. Observation

Start with what feels missing, confusing, weak, generic, or under-explained.

Example observations:

- The homepage proves projects, but not personality.
- The Odoo page has evidence, but the development process feels too stacked.
- The portfolio feels active in reality, but not visually alive.

---

## 2. Visitor Question

Ask what the visitor is likely asking at that point.

Examples:

- What does this person actually do?
- How did he learn these capabilities?
- Is this real work?
- Why should I open the Odoo case study?
- Is he only using AI, or does he understand the business?

---

## 3. Desired Emotion

Define what the visitor should feel.

Examples:

- This person is practical.
- This person understands operations.
- This person learns through real problems.
- This person is actively building.
- I want to speak with him.

---

## 4. Story

Define the story before defining the component.

Bad starting point:

> Add a timeline.

Better starting point:

> Show that curiosity became capability, and each capability made the next problem easier to solve.

---

## 5. Content

Write the content before designing the layout.

This includes:

- Section title
- Lead copy
- Key stages
- Labels
- Supporting notes
- Public-safe boundaries
- What should not be said

---

## 6. Visual Metaphor

Choose a metaphor that matches the story.

Examples:

- Capability graph
- Translation board
- Workflow path
- Review signal dashboard
- Thinking lab cards
- Living workbench

Avoid choosing visuals only because they look modern.

---

## 7. Interaction

Interaction should help visitors understand the story.

Acceptable interaction:

- Click a graph node to reveal how a capability started and where it is still used.
- Filter project cards by focus.
- Expand an idea card to see problem, why it matters, and possible direction.

Avoid:

- Decorative-only animation
- Accordion text that hides important meaning
- Complex interaction that distracts from the story

---

## 8. Prototype

Before full implementation, create a small prototype or mockup.

Prototype goals:

- Check whether the story is understandable
- Check whether the visual metaphor makes sense
- Check desktop and mobile feasibility
- Avoid overbuilding a weak idea

---

## 9. Implementation

Only implement after the previous steps are clear.

Implementation should be:

- Minimal
- Public-safe
- Responsive
- Aligned with existing style
- Easy to maintain

---

## 10. QA

Check:

- Desktop visual clarity
- Mobile behavior
- Link integrity
- Accessibility basics
- No horizontal overflow
- No broken existing sections
- No confidential data
- No fake metrics

---

## 11. Reflection

After QA, ask:

- Did this section create the intended feeling?
- Did the visual metaphor work?
- Did the visitor journey improve?
- Should anything be simplified?

---

## 12. Documentation

Every meaningful update should be documented.

Documentation should include:

- What changed
- Why it changed
- What was intentionally not changed
- Any limitation
- Next recommended step

---

## Rule of Thumb

If we cannot explain what a feature helps visitors discover, we should not build it yet.
