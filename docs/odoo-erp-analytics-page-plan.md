## 1. Purpose

This document defines the planned structure, content direction, visual evidence, and implementation boundaries for the Odoo ERP Analytics case study page.

The purpose is to make the Odoo ERP Analytics page a flagship portfolio case study that clearly supports Fauzan Widianto's positioning as a:

**Business Systems & Operations Analytics professional**

The page should show how ERP transaction data, operational process knowledge, SQL logic, dashboard/reporting design, and business-rule validation can be combined into practical management visibility.

This document must be reviewed before making further changes to the Odoo ERP Analytics HTML page.

---

## 2. Relationship to Portfolio Design Guide

This page must follow the rules in:

```text
docs/portfolio-design-guide.md
```

The homepage is the visual source of truth.

The Odoo page should not feel like a separate dark SaaS landing page. It should feel like a detailed case study inside the same warm, calm, business analytics portfolio.

The default page direction should be:

- Light like the homepage
- Warm off-white background
- Dark teal accent
- White cards
- Soft borders
- Rounded corners
- Business-first language
- Clear visual proof
- Careful AI positioning
- No confidential information

---

## 3. Page Goal

The Odoo ERP Analytics page should answer this question:

> Can Fauzan understand a complex ERP business flow, identify reporting gaps, validate data logic, and turn operational records into practical visibility for management review?

The page should make the reader understand:

- What business problem existed
- Why standard ERP reporting was not enough
- What role Fauzan played
- How the ERP flow was mapped
- How the data logic was structured
- What kind of dashboard/reporting output was created
- How the project supports management review and operational follow-up
- What skills this project demonstrates

---

## 4. Target Reader

The page is mainly for:

- Recruiters
- Hiring managers
- Business analysts
- Operations leaders
- Finance / commercial review stakeholders
- BI / data analytics hiring teams
- Digital transformation / ERP teams

The reader may not be deeply technical.

The page must explain technical work in business language first, then support it with enough technical detail to show credibility.

---

## 5. Core Message

The core message of the page is:

> This project turned scattered Odoo ERP transaction data into structured operational visibility for management review, by combining ERP process understanding, SQL/data logic, dashboard design, and business-rule validation.

The page should not be positioned as only:

> I built a dashboard.

The stronger positioning is:

> I understood how the business process works inside the ERP, mapped the transaction flow, validated the source of truth, and built a reporting structure that helps people review operations more clearly.

## 7. AI Positioning for This Page

AI should be mentioned carefully.

AI can be included as part of the workflow, but it should not be one of the main hero tags.

Preferred language:

> Used AI-supported development tools to speed up iteration, documentation, and implementation, while keeping business-rule validation and final review human-led.

Avoid:

> AI-powered ERP analytics engine.

Avoid making the project sound like the value came mainly from AI. The value should come from business understanding, ERP logic, and structured reporting.

### Preferred Hero Tags

```text
Business Operations
ERP Analytics
PostgreSQL / SQL
Dashboard & Reporting
Process Visibility
```

AI can be mentioned later in the workflow or skills demonstrated section.

## 13. Section 3 - Problem / Context

### Purpose

Explain why the project mattered.

The problem should be written in business language, not technical language.

### Proposed Heading

```text
The issue was not just data. It was business visibility.
```

### Proposed Content

```text
After ERP migration, standard Odoo reporting was useful but not enough to answer practical management questions quickly. Operational review often required checking several ERP menus, comparing transaction flows manually, and interpreting how sales, procurement, inventory, production, invoicing, and payment records connected to each other.

The challenge was not only technical extraction. The real challenge was understanding how ERP transactions represented actual business processes, identifying the source of truth, validating business rules, and turning scattered operational records into dashboard-ready views.
```

### Notes

This section should be a narrative block, not too many cards.

## 15. Section 5 - Approach / Workflow

### Purpose

Show how Fauzan thinks and works.

This section should demonstrate business analysis, data validation, and structured problem solving.

### Proposed Heading

```text
From business questions to validated analytics logic
```

### Proposed Workflow Cards

#### 01 - Clarify the business question

Define what management needs to review: order status, source, fulfillment progress, billing, payment, and profitability signals.

#### 02 - Map the ERP flow

Understand how transactions move across sales, internal orders, procurement, manufacturing, stock movement, invoicing, and finance.

#### 03 - Validate the source of truth

Review field relationships, custom references, transaction statuses, exceptions, and business meaning before creating reporting logic.

#### 04 - Build analytics logic

Use PostgreSQL and SQL to structure reporting views that summarize operational activity into reusable dashboard datasets.

#### 05 - Design dashboard views

Organize information into familiar operational review views instead of overwhelming users with raw database complexity.

#### 06 - Review with business context

Use modern tools to speed up iteration while keeping human judgment on business rules, data quality, and decision usefulness.

### Notes

AI can be referenced in step 6, but the wording should stay mature and not too AI-heavy.

## 16. Section 6 - Architecture Diagram

### Purpose

Explain how ERP data becomes management visibility.

The architecture should be understandable to non-technical business readers.

### Proposed Heading

```text
How ERP transactions become reviewable business visibility
```

### Recommended Diagram Flow

```text
Odoo ERP Source
↓
PostgreSQL / SQL Extraction
↓
Business Logic & Validation Layer
↓
Analytics Views / Dashboard Data
↓
Dashboard + Excel Export
↓
Management Review / Operational Follow-up
```

### Detailed Diagram Content

| Layer | Content |
|---|---|
| Odoo ERP Source | Sales orders, internal orders, purchase orders, manufacturing orders, stock movement, invoices, payments |
| SQL Extraction | Read-only queries, company filter, canceled-state exclusion, reference mapping |
| Business Logic & Validation | Source classification, SO/IO/JO relationship checks, status logic, exception handling, profitability signals |
| Analytics Views | Sales Order View, Internal Order View, Material Tracking, Invoice & Payment View |
| Dashboard & Export | Web dashboard, searchable tables, filters, Excel export |
| Decision Support | Management review, operational follow-up, issue investigation, cross-functional coordination |

### Implementation Direction

The diagram should be built in HTML/CSS first.

Avoid using an image-only diagram unless needed, because HTML/CSS is easier to update and keep responsive.
