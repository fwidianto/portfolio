## 1. Purpose

This file identifies what should be improved on the homepage before editing it again.

The homepage should now support the stronger direction that emerged from the Odoo ERP Analytics case study page.

The current direction is:

```text
Business Systems & Operations Analytics
```

The homepage should introduce Fauzan as someone who connects business process, ERP systems, operational data, dashboard/reporting workflow, and AI-assisted delivery into practical management visibility.

This document exists so future homepage updates do not become scattered or disconnected from the project page direction.

---

## 2. Main homepage problem to solve

The improved Odoo page now tells a clearer story than the homepage.

The homepage needs to catch up.

The homepage should not only say:

```text
I do data, reporting, automation, and AI-assisted work.
```

The homepage should say, more clearly:

```text
I help turn messy operational and ERP data into structured visibility for management review, business follow-up, and better operational decisions.
```

The homepage should act as the entry point to the Odoo page, not feel like a separate older version of the portfolio.

---

## 3. What we learned from the Odoo case study page

The Odoo page improved when it moved from a dashboard-only story into a business systems story.

Useful patterns to bring back to the homepage:

1. Shorter, more meaningful copy.
2. More visual proof.
3. Clearer business-first positioning.
4. Less generic project wording.
5. More emphasis on practical management visibility.
6. More human explanation of how problems were solved.
7. Public-safe project evidence.
8. An insight layer: not only showing data, but showing what needs attention.

The homepage should use the same thinking.

---

## 4. Homepage positioning target

Recommended homepage positioning:

```text
Business Systems & Operations Analytics
```

Supporting keywords:

- ERP process understanding
- Operations analytics
- Dashboard and reporting workflow
- Data validation
- Operational traceability
- Management visibility
- Profitability review support
- Cross-functional coordination
- Practical automation
- AI-assisted delivery with human-led validation

Avoid over-positioning as:

- Software developer
- AI engineer
- Full-stack developer
- Experimental AI builder
- Generic data analyst only

The homepage should make it clear that the strongest value is the ability to understand business processes and translate them into useful data/reporting structures.

## 5. Sections that likely need improvement

### 5.1 Hero section

Current issue:

The hero is generally good, but it may still sound broad and generic.

Improvement target:

Make the first screen more aligned with the Odoo case study direction.

Possible direction:

```text
Business systems, reporting, and operations insight for clearer management decisions
```

Possible supporting copy:

```text
I help turn ERP context, operational workflows, and reporting problems into structured dashboards, review logic, and practical visibility for business teams.
```

Important:

- Keep the language simple and recruiter-friendly.
- Do not overuse AI in the hero.
- AI can remain as workflow support, not the core identity.

---

### 5.2 Profile card / role label

Current issue:

The role may still be too broad as `Data & Business Analytics Professional`.

Possible improvement:

Use a role label closer to:

```text
Business Systems & Operations Analytics
```

or:

```text
Operations Analytics & ERP Reporting
```

Keep it human and not too long.

---

### 5.3 Analytics Focus / About section

Current issue:

The section may explain capabilities, but it should better connect them into one working identity.

Improvement target:

Make the section explain how the work is done:

```text
Business process understanding -> data validation -> reporting logic -> dashboard / workflow output -> management review
```

Suggested themes:

- Understand the business process first.
- Validate what the data means inside the ERP/workflow.
- Build reporting structures that answer practical business questions.
- Use AI-assisted tools to speed up iteration, but keep business judgment human-led.

---

### 5.4 Workflow section

Current issue:

The homepage workflow should mirror the stronger case-study logic.

Recommended homepage workflow:

```text
1. Understand the business question
2. Map the process and source data
3. Validate business rules and exceptions
4. Build reporting / dashboard logic
5. Turn outputs into review-ready visibility
6. Iterate with tools and human judgment
```

This is important because it helps the homepage explain how the Odoo project was built without forcing the reader to open the project page first.

---

### 5.5 Projects section

Current issue:

The Odoo project should now become the flagship project.

Improvement target:

Make the Odoo project card more prominent and more specific.

The Odoo card should not only say it is an ERP dashboard. It should say it turns scattered Odoo transactions into operational visibility and review signals.

Suggested Odoo card direction:

```text
Odoo ERP Analytics Case Study
```

Suggested description:

```text
A public-safe case study on turning Odoo ERP transactions into management-ready visibility, including order traceability, material tracking, review signals, and operational follow-up logic.
```

Suggested tags:

- ERP Analytics
- Operations Visibility
- Review Signals
- SQL / Dashboard
- Public-Safe Case Study

---

### 5.6 Project cards in general

Current issue:

Other project cards may feel disconnected from the new Odoo case-study standard.

Improvement target:

Each project card should answer:

- What business problem does it solve?
- What output does it show?
- What skill does it prove?
- Is there visual proof or a public-safe explanation?

Avoid project cards that only say:

```text
Built using Python, Flask, SQL, HTML, CSS.
```

Better pattern:

```text
Built to make operational review faster by connecting scattered data into searchable reporting views.
```

---

### 5.7 Featured proof / flagship project block

Potential improvement:

Add a stronger featured block for the Odoo case study.

Purpose:

Make the homepage immediately show one strong proof point, instead of making all projects look equal.

Possible block title:

```text
Flagship Case Study
```

Possible heading:

```text
Odoo ERP Analytics: from scattered transactions to review-ready visibility
```

Possible short copy:

```text
A public-safe project case study showing how ERP records were mapped, validated, and turned into dashboard views, output evidence, and review signals for operational follow-up.
```

This would help the homepage connect directly to the improved project page.

---

### 5.8 Skills / tools presentation

Current issue:

Tools should support the story, not dominate it.

Improvement target:

Group skills by business use:

- ERP & business systems: Odoo, SAP ECC6
- Analytics & reporting: SQL, Looker Studio, dashboards, Excel/Sheets
- Automation & workflow: Apps Script, VBA, UiPath, Python
- AI-assisted delivery: Codex, OpenHands, ChatGPT
- Business review: profitability, operations, procurement, sales order, invoice/payment follow-up

This is better than a raw tool list.

---

### 5.9 AI positioning

Current issue:

AI should not become the main identity.

Improvement target:

Use AI as workflow support.

Preferred wording:

```text
AI-assisted iteration and documentation, with human-led business-rule validation.
```

Avoid:

```text
AI-powered ERP intelligence engine.
```

The homepage should show that the user can use modern tools without pretending to be primarily an AI engineer.

---

### 5.10 Visual style consistency

Current issue:

The Odoo page now has a stronger warm case-study direction. The homepage should not feel disconnected.

Improvement target:

Check whether the homepage should gradually become:

- warmer
- lighter
- calmer
- more business-consultant style
- less dark / tech startup style

Important:

Do not redesign everything at once unless necessary.

A first homepage pass should focus on positioning, copy, project cards, and one flagship project block.

---

## 6. Recommended homepage update order

Do not update everything randomly.

Recommended sequence:

```text
Phase 1 - Positioning and copy
- Update hero title/subtitle
- Update role label
- Update Analytics Focus/About section wording

Phase 2 - Homepage structure
- Add or strengthen a short workflow section
- Make the Odoo case study a flagship proof block
- Improve project card wording

Phase 3 - Visual alignment
- Adjust spacing and card hierarchy
- Make project section feel more like the improved Odoo case-study direction
- Reduce generic/dark-tech feel if needed

Phase 4 - Final review
- Check mobile layout
- Check project links
- Check CV link
- Check public-safe wording
- Check whether homepage and Odoo page feel like the same portfolio
```

## 9. Odoo page future improvement note: Learning Development / Technical Architecture

For the next future improvement of the Odoo case study page, consider adding a section about the learning and development journey.

Possible section name:

```text
Learning Development / Technical Architecture
```

or:

```text
How the Project Was Built
```

or:

```text
Development Notes: Problems, Tools, and Technical Architecture
```

Purpose:

Show not only the final dashboard, but also what problems were discovered while building it and how tools were used to solve them.

Topics to include later:

1. Problems found during development
   - ERP data relationships were not straightforward.
   - Standard reports did not directly answer management review questions.
   - Source-of-truth fields had to be checked carefully.
   - Custom Odoo fields required interpretation.
   - Some links between SO, IO, PO, MO, DO, invoice, and payment needed validation.
   - Public portfolio evidence had to be created without exposing confidential data.

2. Tools used and how they were used
   - Odoo 16 as ERP source.
   - PostgreSQL / SQL for extraction and analytics logic.
   - Python / Flask for backend dashboard layer, where applicable.
   - HTML / CSS / JavaScript for dashboard presentation.
   - Excel export for familiar business review workflow.
   - GitHub for version control and documentation.
   - AI-assisted tools for faster iteration, documentation, and debugging, with human-led validation.

3. Technical architecture explanation
   - ERP source tables/views.
   - SQL extraction and validation layer.
   - Business-rule mapping.
   - Dashboard/API layer.
   - Frontend review views.
   - Export/reporting workflow.
   - Public-safe portfolio layer.

4. What was learned
   - Good dashboards require business-rule understanding, not only technical extraction.
   - ERP migration creates reporting gaps that need process knowledge.
   - Public portfolio work requires a separate confidentiality layer.
   - AI tools are useful for speed, but business judgment remains the control point.

Important rule:

This future Odoo section should be more technical than the current page, but still business-readable. It should not make the page feel too developer-like.

Recommended placement later:

After Architecture / Data Flow, or after Review Signals, depending on page length.
